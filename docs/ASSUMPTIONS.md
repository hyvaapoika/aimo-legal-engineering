# Implementation decisions and limits

## Current kitchen purchasing agent

Delivery is entered in the prompt and resolved by a bounded deterministic parser (ISO, Finnish numeric date, English weekday or relative day), then shown in the review. No date retains the existing default/prior date. Unsupported or conflicting recognized expressions need clarification. Attachment-only delivery dates and conversational weekly order-history lookup are not implemented.

`/agent` adds persisted kitchen profiles and owned purchase plans to the existing local webshop. Gemini text/image/audio interpretation is advisory and strictly validated; a bounded deterministic workflow handles recipe quantities, claims, offers, substitutions, budgets and export. It cannot approve or place orders. Exact/approved kitchen choices persist into cart suggestions, while existing server mandates and human approval remain authoritative.

The two starter kitchens are editable examples under the demo customer, not connected restaurant accounts or learned history. Only three reviewed recipes are installed. Unknown recipes, amounts, pack conversions and stock are not invented. Pantry is supplied by the chef, not an inventory feed. No live menu crawler, replenishment scheduler, learned purchasing model or autonomous sales outreach exists.

Live Gemini tests succeeded for a typed hotel order and synthetic menu-photo/WAV requests. The physical browser microphone has not been tested. Voice is recorded input, not a real-time conversation or phone call. Raw attachments are not saved in plan records; they are sent to Gemini on explicit Prepare. The process-local job runner marks interrupted tasks retryable after two minutes rather than resuming them. Mock supplier prices and stock, limited verified photos, localhost-only buyer access, and separate human approval remain unchanged. See `KITCHEN-AGENT-DEMO.md`.

## Current smart-webshop verification (14 November 2026)

The full-catalogue storefront is implemented locally. Gemini structured interpretation was exercised with the supplied server-side key; all 17,546 static documents were embedded with a local multilingual MiniLM model after the Gemini embedding quota was exhausted. No paid upgrade or managed vector service was enabled. Earlier provider-status notes below describe earlier implementation stages.

The browser flow used mock prices/stock, five verified product-photo mappings, and explicit placeholders for the remaining images. No official image endpoint or taxonomy mapping was supplied. Broad navigation/product-type labels are application heuristics, never supplier declarations. Semantic scores are not confidence or suitability guarantees.

The storefront uses a local demo buyer through a buyer-only server proxy. Production requests to that proxy are refused until buyer authentication exists. Human credentials and approval remain separate. The search read store uses PGlite/pgvector even when the commercial database uses PostgreSQL; a hosted PostgreSQL discovery adapter has not been implemented or tested. Commercial SQL transaction paths were not migrated in this change.

Browser verification reached a held human-review proposal, with existing category and weekly-budget holds still enforced. Local tests also exercise the established approval/order/ledger flow. No real supplier fulfilment, public deployment, or new telephone integration was exercised. See `SMART-WEBSHOP-DEMO.md` for setup and evaluation limits.


The sections below record earlier implementation stages where explicitly labelled. The current storefront supersedes those UI previews; catalogue-wide photography and production buyer authentication are still outstanding.

## Current live recipe workspace

Three curated recipes were read from Valio Aimo's public recipe pages on 14 November 2026, separately from the hackathon catalogue: [tomato and basil pasta](https://www.valioaimo.fi/reseptit/tuorepastaa-tomaatti-basilikakastikkeella/), [Palermo vegetable pasta](https://www.valioaimo.fi/reseptit/palermon-kasvispasta/), and [sweet chilli chicken pasta](https://www.valioaimo.fi/reseptit/paholaisen-kanapasta-kylmavalmistus/). Published yields and ingredient weights are retained in `packages/discovery/src/recipes-data.json`; official photo provenance is in `apps/web/public/recipes/sources.json`. The browser offers these three recipes only. It does not crawl new recipes or generate unreviewed ingredient quantities.

Recipe matching and bounded portion/pantry interpretation run locally as text changes. These are explicit supported operations, not an unrestricted conversational agent. Gemini is used for background product-query interpretation. Saved baskets in this browser provide the only preference history; real customer purchases and inventory are not connected. Recipe ingredients are mapped to reviewed product candidates where available, and the chef can change them. A candidate match does not certify whole-meal dietary suitability. No automatic KG-to-L density conversion is used. Missing source amounts and missing verified pack contents require manual quantities.

The [OpenUI renderer](https://www.openui.com/docs/openui-lang/renderer) was reviewed. No OpenUI dependency or generated UI language is installed: the application already renders typed React recipe/product/quantity controls. The revised visual design does not change the localhost-only authentication boundary or make the application production-ready. Prices remain explicitly marked as sample data in mock mode.

## Complementary products in product details

“Goes well with this” is a curated recommendation feature, not a trained collaborative-filtering system. Known food types and a small set of ingredient-name rules select meal components; verified recipes and actual locally saved co-occurrence provide additional candidates. Unsupported products can have no recommendations. The app does not invent population-level purchasing patterns, margins, customer orders or conversion uplift. Candidate products and offers come from the existing catalogue and supplier adapter, with known stock, pricing and explicit dietary requirements checked before display. At most three groups are displayed; adding one suppresses other candidates from that group. This is not whole-meal allergen certification. New adds are explicit, use whole packaged sales units, retain requirements, and undergo normal checkout revalidation. Images remain limited to the verified mappings; placeholders are used otherwise.

## Proactive replacement suggestions

Alternatives are fetched automatically in product details and relevant shopping contexts. The initial policy surfaces one option for a verified shortage or at least €1 lower converted total; this threshold is an application choice, not a learned user preference. Details can also show a neutral pack alternative. Supplier-listed or same-type/category candidates still require the chef's suitability judgment. Quantity, dietary declarations, comparable units and sufficient known stock are checked in TypeScript; unknown stock is never promoted as available. Savings compare complete rounded sales-pack totals and state excess contents. Mock prices remain labelled, so the measured savings are demo illustrations, not a real supplier discount. Swaps remain explicit and checkout revalidates signed offers.

## Data and money

- All 17,546 supplied product records are available locally. Original JSON, its schema, carbon CSV, reliability CSV, and the pasted upstream OpenAPI are preserved. They are not redownloaded at startup.
- Mock prices and availability are synthetic and labelled `source: mock`. They are not captured Valio responses. Named scenario fixtures are in `data/fixtures/scenarios.json`; other products receive a deterministic synthetic fallback price in mock mode only. Live mode never falls back to mock.
- `469363` is milk and `469380` is coconut milk. The plan incorrectly calls these yoghurt. The demo uses yoghurt `476824` (blocked) and `476812` (substitute), butter `475797`, fish `461885` (short) and `461868` (substitute), and milk `464201`.
- Manufacturer base-unit volume/net weight is preferred; KG base units represent one kilogram even when a physical fish box weighs ten kilograms. Conservative name parsing is explicitly marked inferred. Multipacks and variable-weight names without a verified conversion remain unknown.
- One supplied pack conversion has a zero factor. It is excluded; no division by zero or invented sales-pack factor is allowed. A product’s own base unit has factor one by definition.
- Supplier generic `0.01` lot sizes do not authorize fractional packaged pieces. Conversion rounds requirements up to whole pieces and to the supplier lot. The API also rejects fractional-piece proposals independently.
- All money is EUR. Decimal arithmetic computes each line; half-up rounding to integer cents happens once per line. The server computes totals from stored, verified offers. Buyer-provided totals and customer identity fields are rejected.
- Supplier offsetless timestamps use Europe/Helsinki, including daylight saving. Date-only price expiry includes the full Helsinki day. Requested delivery dates must match the signed offers.
- Required dietary/allergen claims need positive declarations. Lactose-free is not milk-allergen-free. Empty declarations remain unknown. Strict substitutions also preserve the original product’s positive free-from declarations.
- Reliability and carbon are comparison signals, not promises. Missing signals are absent. No approximate order-level carbon total is presented; the plan’s dairy-density estimate is therefore not used.
- Official category labels are absent. Current discovery combines an immediate in-memory suggestion path with background PGlite full-text/trigram and optional local pgvector retrieval. The older catalogue endpoint remains deterministic; neither search path changes supplier declarations.

## Authority and approvals

- Orders are always simulated because the supplied API has no order endpoint. There is no payment, ERP submission, stock reservation, or supplier confirmation.
- In the running local demo, every feasible quotation is HOLD until a registered human approves it. The underlying rules library retains AUTO for explicitly configured non-demo integrations, only after all code checks pass. A HOLD requires an authenticated registered approver. REFUSE is never overridden. A human may override spending/category/site/substitution/anomaly policy holds, but not unknown stock, unavailable stock, late delivery, or hard refusals. Supplier feasibility must be resolved first.
- Partial automatic placement is deliberately disabled. A global order/week limit applies to the whole proposal, so splitting cannot bypass it. The demo illustrates AUTO and HOLD using separate proposals.
- Amending quantities creates a linked replacement proposal and evaluates all rules again. A new HOLD returns to the human; a valid AUTO can place after the human’s explicit amendment. The old approval resolves as amended. Callback leaves the decision pending.
- Approvals are bound to a hash of immutable lines, a challenge token, and a revision. First decision wins. Approval and order placement are atomic. Existing prices, signatures, agent activity, mandate, and current spending are checked again at approval time.
- The local workspace has one customer (`hotel-haven`) and one human administrator/approver (`maija`). This is an explicitly configured demo identity, not SSO. Agents are separate principals with customer binding and scoped permissions. The schema supports multiple customers; the human UI is intentionally single-workspace.
- `ALLOW_BEARER` is an interoperability fallback for clients without request signing. Admin and agent credentials are separate. Default demo tokens are accepted only for local mock development. The development gateway binds to loopback.
- Provider keys never appear in the browser. Browser sessions are HMAC-authenticated, HttpOnly, SameSite Strict, expire after eight hours, and become invalid when the admin token rotates. Mutations require a matching Origin.

## Persistence and operations

- PGlite provides embedded PostgreSQL persistence for a zero-service demo. External PostgreSQL uses `pg`. A small parameterized SQL repository replaces Drizzle. Versioned mandates, signed offers, proposals, verdicts, approvals, orders, nonces, and ledger records are persisted in transactional JSONB tables with uniqueness constraints.
- Business transitions serialize to protect rolling limits and prevent duplicate orders. External PostgreSQL also uses an advisory lock. This is appropriate for a demo, not a high-throughput deployment design.
- A persistent approval-routing state and timer replace pg-boss. Restarting retains pending approval/expiry state. App inbox is always available. Unsupported voice/SMS attempts are recorded as disabled and fall back to the app; they are never reported as delivered.
- Browser voice is implemented with ElevenLabs WebRTC. Telephone/SMS routing remains unconnected; `VOICE_ENABLED` still refers to that unconfigured legacy telephony path. Browser voice uses the existing private ElevenLabs agent and server-minted short-lived tokens, and is limited to local mock demo mode.
- Browser voice accepts ordinary approval/cancellation requests followed by a separate natural confirmation (for example “place the order” then “yeah, go ahead”). Gemini can propose a confirmation for other wording through a client tool, but that tool cannot save a decision. The final human confirmation and quotation checks are enforced by TypeScript. Questions, conditions, AI messages, silence and confirmations without a pending action do not approve. Clear negative requests such as “don’t approve it” propose rejection, never approval. Any intervening user utterance or a 30-second delay cancels the armed decision. Session lifetime is five minutes; conversations are capped at three minutes. Provider queueing is disabled to avoid hidden hold music.
- This is an authenticated-browser demo trust model, not voice identity verification: a logged-in human browser can submit transcript text, just as it can click Approve. The transcript is NOT cryptographically attested by ElevenLabs. No PIN or voiceprint is used. Buyer/model endpoints cannot invoke these admin routes. Do not deploy this as production telephone authorization.
- Quotation context comes from stored offers. Voice sessions bind approval ID, revision, challenge and line hash; final decisions use existing transactional revalidation and ordering. A hash of the two decision utterances and session ID is included in decision evidence; full provider conversation recordings/transcripts may remain in ElevenLabs under its account retention settings. Browser transcripts are held in component memory.
- Voice sessions are in memory on one gateway process. Restarting the gateway invalidates them without resolving the quotation. Localhost works for microphone access; a physical phone requires a trusted HTTPS deployment. No public phone-accessible endpoint has been deployed.
- The optional Claude Agent SDK client and Gemini structured advisory reviewer are implemented and typechecked. They were not run against paid APIs because no keys were supplied. Gemini has no authority or tools; its output cannot alter quantities, prices, permissions, or verdicts.
- Business actions and agent reads produce audit events. Passive human dashboard polling and health checks deliberately do not create a new event every few seconds. The single global chain verifies all events; a customer-filtered export is a projection, not an independently verifiable full chain.
- Hash chaining detects altered rows or internal deletion. It does not defeat a database administrator who can rewrite the whole chain, or detect removal of the tail without a previously trusted head hash. Production needs external anchoring and database write-role restrictions.
- Offer validity is min(price expiry, cut-off, issue time + 30 minutes). Supplier price intervals are checked against the requested delivery date. Unpriced products remain unpriced.

## Interoperability and external verification

- The SDK integration test initializes a real Streamable HTTP MCP client and completes search, offers, proposal, and order retrieval. The stdio bridge makes the same tools available to local desktop clients. A public HTTPS Railway deployment is live. Its 17,546-record catalogue, lightweight search endpoints, health route, public demo sign-in, storefront context, and one read-only Valio offer lookup have been verified. The complete purchasing journey has not been written to its shared ledger during hosted verification. A real Claude Desktop connection remains untested.
- Discovery is UCP-shaped, and the agent card describes the interface. The server does not implement an A2A task-execution endpoint or claim UCP/A2A protocol certification.
- JWS uses Ed25519. HTTP signing implements a restricted RFC 9421 profile with fixed covered components; arbitrary component lists and signature labels are unsupported. The full target URI is signed, protecting host and query parameters. Proxies must preserve the external request URI.
- XML export uses the UBL Order 2.1 envelope and Peppol Ordering identifiers. It escapes data and is checked for well-formed XML. Placeholder GLNs, supplier unit mapping, and customer legal data prevent real Peppol transmission. It has **not** passed a complete Peppol Schematron/UBL conformance suite; do not call it certified or production-valid.
- A disposable local PostgreSQL 16 instance passed the end-to-end and concurrent-approval checks. The hosted demo uses persistent PGlite rather than PostgreSQL. Hosted proposal/approval/order writes, production model billing, real customer SSO, and telephone/SMS still need separate environment-backed verification. The hosted order adapter remains simulated.

Standards consulted: [MCP TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk/tree/v1.x), [PGlite persistence and transactions](https://pglite.dev/docs/api), [Peppol Ordering identifiers](https://docs.peppol.eu/poacc/upgrade-3/profiles/28-ordering/), and the locally installed Next.js route-handler documentation. The upstream request contract comes from the user-supplied OpenAPI file.
